# Bot settings (dashboard-managed)

The owner changes the bot's important switches and numbers from the dashboard's Settings tab, without a restart or a deploy. This page describes the bot side: the registry, the precedence, the tables, the settings goroutine, the change digest and the Telegram profile push. The dashboard only queues change requests; the bot validates and applies them within about 2 s. Changes that need the owner's Approve in Telegram (raising a budget, lowering the HikerAPI price, a free-service host) wait for the owner's tap first (see "Telegram approval").

## Precedence

For every managed setting the bot uses, in this order:

1. the value the owner set (`bot_settings`), validated with the registry;
2. the `.env` variable, parsed exactly as before;
3. the code default.

With empty tables (the state after migration 011) every getter returns what it returned before, for any `.env`; `config/settings_test.go` proves it against copies of the previous getters (`config/head_getters_test.go`). `.env` stays the fallback: a key without a row, a reset, and a start whose settings read fails without a cache file all use it. A bot without a database configured (no `DB_*` variable set, and `InitDatabase` failed) leaves the settings inert: no snapshot, no cache file read or written, no alert, so every getter reads `.env` and its default exactly as before. A configured database that `InitDatabase` could not open at start (down, unreachable) is not "no database": the start falls back to the cache file like a failed settings read (below), so a platform the owner switched off stays off.

Exceptions:

- A stored value that no longer validates (for example after a range was narrowed in code) is skipped and logged once, so `.env` or the default applies. For money and payment keys it gives the key's safe value instead (budgets 0, HikerAPI price 1 USD, Stars off) and alerts the owner once, so a narrowed range never turns spending back on through `.env`.
- Hard ceilings apply to stored values only; `.env` values keep working as before.

## Registry (`model/settings`)

One entry per key: type, range, hard ceiling, `.env` variable, default, approval rule, safe value, and the label and impact text the owner sees. It is pure data plus stdlib validation (no I/O, nothing to change at runtime), like `model/reportreply`. The bot publishes it as `bot_runtime_status.registry`, so the dashboard needs no copy of its own.

| Group | Keys | `.env` |
|---|---|---|
| Platforms | `platform.<p>.enabled` for instagram, tiktok, twitter, youtube, reddit, facebook, 9gag, threads; `platform.instagram.fixed_link_service` | `ENABLE_<P>`, `INSTAGRAM_SERVICE` |
| Free services | `service.<name>.host` for kkinstagram, kktiktok, vxreddit, facebed | `<NAME>_HOST` |
| Paid providers & budgets | `paid.apify.monthly_budget_usd`, `paid.hiker.monthly_budget_usd`, `paid.hiker.price_per_request_usd`, `paid.instagram.provider_order`, `alerts.hiker_low_balance_requests` | `APIFY_MONTHLY_BUDGET_USD`, `HIKERAPI_*`, `INSTAGRAM_PAID_PROVIDERS` |
| Special downloads | `gated.global_monthly_cap`, `gated.user_monthly_allowance`, `gated.chat_monthly_cap` | `GATED_FETCH_*` |
| Stars and limits | `stars.enabled`, `limits.default_daily_media` | `STARS_SUPPORT_ENABLED`, `DEFAULT_DAILY_MEDIA_LIMIT` |

Hard ceilings (raising one needs a code change and a deploy): Apify budget 20 USD a month, HikerAPI budget 10 USD a month, bot-wide special downloads 5000 a month, per person and per group 1000 a month.

Approval rules (data in the registry): raising a dollar budget (also from 0, which is how a provider is switched on), lowering the HikerAPI price, and any change of a `service.*.host` wait for the owner's Approve in Telegram. Everything else, Stars on included, applies directly. Without `ADMIN_USER_ID` there is nobody to ask, so a request that needs approval is rejected with "needs the owner's approval, but ADMIN_USER_ID is not set".

Never managed from the dashboard: tokens and other secrets, `ADMIN_USER_ID`, database and dashboard settings, Apify actor ids, payout links and addresses, the Stars tiers, the relay settings.

## Tables (migration `011_bot_settings`)

| Table | What |
|---|---|
| `bot_settings` | key, value (JSONB, at most 2 KB), `updated_at`, `updated_by`. Written by the bot when it applies a request; a trigger stamps `updated_by` from the writing transaction's `app.settings_actor` (`manual` when unset). `TRUNCATE` is refused |
| `settings_audit` | append-only history, one row per write of `bot_settings` (old and new value, actor, `db_role` = `current_user`, request id), filled by a trigger; `UPDATE`, `DELETE` and `TRUNCATE` are refused |
| `settings_change_requests` | what the dashboard asks for: it inserts `kind`, `key`, `value` (NULL = reset) and `expected` (the value the page showed) only. One open request per key (a unique index, so a second one fails at INSERT). A queued request expires 10 minutes after it was made; one awaiting the owner's approval 15 minutes after the bot asked (`expires_at` is reset then, `approval_message_id` holds the Telegram message) |
| `bot_runtime_status` | what the bot reports, one JSON blob per component: `bot` (start, heartbeat, commit, where the settings came from), `secrets` (set or not; never values), `settings` (effective value, source and whether `.env` sets it, per key), `registry` (with `special_limit`, see below), `profile` (last profile push and its error), `paid` and `relay` (see "Paid services and home relay state"), `services` (see "External services health") |

The down migration drops the four tables; a rollback is deploying the previous commit instead, which ignores them. The triggers need PostgreSQL 14 or later.

Grants for the dashboard role are an owner step on the server: `SELECT` on the four tables, `INSERT (kind, key, value, expected)` on `settings_change_requests` and `USAGE` on `settings_change_requests_id_seq`, nothing else (`services/botsettings/pg_integration_test.go` checks exactly these). They let the dashboard role change live settings once the bot applies requests, so they are run together with the Settings tab, after the dashboard's hardening (its own listener and reverse-proxy location for the settings API), not before.

## Special-download limits (migration `012_special_limit_requests`)

A second request kind, `special_limit`, sets one person's or group's monthly special-download limit in `gated_fetch_policies` (never in `bot_settings`):

- **Key** `user:<id>` (id above 0) or `chat:<id>` (id below 0), written the canonical way (`model/settings.ParseSpecialLimitKey`). **Value** a whole number from 0 to 1000 (`CeilingGatedMonthlyQuota`), -1 for unlimited (migration `014_special_limit_unlimited`), or SQL NULL to go back to the default. **Expected** the stored `monthly_limit` the page showed: JSON `null` for none, or any whole number from -1 (an unlimited row or a `/gated` value above 1000 can still be compared). Values above 1000 stay Telegram-only (`/gated`, unchanged); turning unlimited on waits for the owner's approval in Telegram (the usual `awaiting_approval` flow, at most 3 waiting, rejected without `ADMIN_USER_ID`), because an unlimited person or group also skips the bot-wide cap, whose raise needs approval; turning it off (a reset or a number) is applied at once. The paid budgets apply either way.
- The bot publishes the rules as `registry.special_limit` (`{"kind":"special_limit","min":0,"max":1000,"unlimited":true}`); a dashboard that finds no such entry knows the running bot does not take limit requests yet.
- **Applied without approval** (except turning unlimited on, see above) in the claim transaction: the claim inserts a missing policy row (enabled, default limit, the same as no row) so it can lock it (`FOR UPDATE`), reads its limit as `StoredCurrent`, and the bot applies the request while that still equals `expected` ("changed meanwhile, reload" otherwise), the value is valid and it differs ("nothing to change: the limit already is …" otherwise). The write sets only `monthly_limit`; `enabled` is kept, so a group switched off with `/gated off` stays off. An expired request reads, locks and inserts nothing. In the same transaction, whatever the decision, a row that holds only the defaults (the claim's lock row, or a reset) is deleted, so no all-default row is left for the group-upgrade copy to carry over.
- After the commit the snapshot, the cache file, the profile and the published settings stay as they are (every special download reads the policy from the database); the change only goes into the owner's change digest, e.g. "• Special downloads a month, group -1001234567890: default (20) → 30 (14:05, dashboard)", rendered from ids and numbers only.
- **Database checks**: the kind CHECK allows `setting` and `special_limit`; CHECKs refuse a bad key, a value that is not a whole number 0-1000, -1 or NULL (a JSON `null` value too), and an `expected` that is not JSON null or a whole number from -1 (`CASE`, so no cast ever fails with an error other than a check violation). The open-request index is per (kind, key): one open request per person or group.
- **Policy audit**: a trigger writes one `settings_audit` row per changed `monthly_limit` (key `special_limit:<scope>:<id>`) and per changed `enabled` (key `special_enabled:<scope>:<id>`) of every write: dashboard requests (actor `dashboard`, request id), `/gated` (actor `telegram`, note "/gated"), the group upgrade copy (actor `bot`, note "group upgraded to supergroup") and `psql` (`manual`). A missing row counts as (enabled, NULL), so an all-default row logs nothing. `TRUNCATE gated_fetch_policies` is refused.
- **Dashboard**: the Limits tab ([dashboard.md](dashboard.md#limits)) sends `POST /api/limits/requests` (`{scope, id, limit, expected}`), checked against `registry.special_limit` (`409` "deploy the bot first" without it, and when the old kind CHECK refuses the row), and follows the request like a setting change. Every request answer carries `kind`. The Settings tab's last-change column leaves the `special_*` audit rows out; its audit log shows them under the group `special_limits`.
- Grants are unchanged: the dashboard role queues limit requests with the same `INSERT (kind, key, value, expected)` grant. The down migration deletes the open and decided `special_limit` requests (the narrow CHECK refuses them) and drops the trigger; the policies and the audit rows stay.

## Paid services and home relay state

Two `bot_runtime_status` components are computed outside the settings goroutine, each by its own refresher goroutine (`services/paid_status.go`, `services/relay_status.go`, started in `app/app.go`, stopped by the shutdown context) every 60 s; the heartbeat only publishes the last snapshot (`Options.PaidStatus`, `Options.RelayStatus`, no I/O), so request processing is never held up. Before the first compute nothing is published. The dashboard's Limits tab shows both as published (with `is_stale` after 3 minutes) on its paid-services and Home relay (NAS) cards; it lists the components `bot`, `settings`, `registry`, `paid` and `relay`.

- **`paid`**: `computed_at`, `order` (`INSTAGRAM_PAID_PROVIDERS`), and per provider its state (`on`, `paused`, `off`, `unknown`) and reason, by the bot's own budget rules. Apify (`apify`): off without a token (`no_token`), paused at a budget of 0 (`budget_zero`) or while the last usage read failed (`usage_unreadable`: the bot refuses runs then), unknown before the first read or after Apify's billing cycle has ended since (`usage_not_read`), else each feature (`posts`, `stories`, `shorts`) whose next run (its cost cap) no longer fits the usage plus the runs in flight is listed in `paused_features`, all three paused being `paused`/`budget_used`. The usage comes from a cache filled by every Apify usage read (each paid run, `/adminstats`, and the hourly health check); it also keeps the account's own limit and billing cycle when Apify sends them (the billing cycle need not be the calendar month the budget is meant for). HikerAPI (`hiker`): off without a token or outside the provider order (`not_listed`), paused at a budget of 0, while the balance is known to be empty (`balance_empty`) or when the next request no longer fits (`budget_used`), paused without a database (`no_database`: its budget needs the ledger), unknown when the ledger could not be read (`ledger_error`); with the month's ledger totals and the last balance read (hourly check, `/adminstats`). No provider API is called for it.
- **`relay`**: `configured`, `platforms_in_use`, and the last `GET /healthz` of the home relay (read every 60 s while it is configured; no token, no platform traffic; it feeds neither the outage tracker nor the hourly probe): `checked_at`, `reachable`, `error` (short, without the URL), `yt_dlp`, `breaker_open`, `global` and `platforms` (enabled, breaker, its time left, calls this hour and day against the relay's limits). A failed read keeps the last answer. `history` aggregates `relay_requests` (migration `013_relay_requests`): one row per call the bot sent to the relay, written in the background so a slow database never delays the video (platform, outcome code `OK`, the relay's error code, `REJECTED` for an answer the bot refused, `TRANSPORT` for a request without an answer, `SKIPPED` for a call that could not be sent for want of the token; the bytes of a delivered video; the duration; no user, chat or video ids), with counts per platform and code for 24 h, 7 d and 30 d and the bytes and average duration of the delivered videos for 24 h and 7 d; null without a database. Rows older than 90 days are pruned once a day by the refresher. A call refused by the bot's own checks (bad id, platform switched off on the relay, no chain time left) is not recorded.

## External services health

The `services` component (`services/services_status.go`) is the health of every external service the bot calls besides yt-dlp, built from the outage tracker (`services/outage_tracker.go`) on every heartbeat (`Options.ServicesStatus`, memory reads only, no I/O). The dashboard shows it on the Platforms tab ("External services", [dashboard.md](dashboard.md#external-services)) and never probes a service itself.

- **Source**: each outage-tracker key keeps the current failure streak, its threshold, the last success, the last failure, when the streak began and the code of the last failure (no counters, no error text). Owner alerts are unchanged: the Telegram alert and recovery messages still carry the raw detail. A success creates a missing entry without a recovery notice, so a service that never failed still shows when it last worked. Besides the existing keys, five call sites report traffic now: `fxtwitter` (FxTwitter API), `tikwm` (tikwm API), `threads-embed` and `vxthreads` (Threads), `9gag-api` (the 9GAG helper script). Each counts only the service's own fault, and a chain deadline that ran out and a failed media download record nothing anywhere. What else is not counted differs per site: FxTwitter ignores 4xx answers other than 429 and an answer without a tweet; Threads embed and vxthreads ignore 4xx answers other than 429 and Meta's "Thread not available" embed, and a post that only quotes another, while any other embed without text or media counts as `parse` (a Meta markup change empties every post) and the Threads login page in place of a vxthreads post counts as `wrong_content` (it is never sent as the post); tikwm counts every non-200 status (a 4xx as `http_4xx`) and ignores only API errors in a 200 answer other than its rate limit, including the free tier's "1 request/second" limit the bot's own concurrent links set off; the 9GAG helper ignores "HTTP 404" and "Post not found in response" (a Cloudflare 403 counts as `http_4xx`), and a local setup problem (no Python with curl_cffi, a missing `scripts/9gag_fetch.py`, or the helper's own "curl_cffi not installed") is only logged, once per process, never recorded as an outage. FxTwitter is counted once per link, from the yt-dlp step (the other steps of the same link call it again without reporting). All five alert at 3 failures in a row like the existing keys.
- **Catalog**: 16 rows in a fixed order: `kkinstagram`, `apify`, `apify-stories`, `hiker`, `instagram-relay`, `kktiktok`, `tikwm`, `fxtwitter`, `youtube-relay`, `apify-youtube`, `youtube-post`, `vxreddit`, `facebed`, `9gag-api`, `threads-embed`, `vxthreads`. Each has a label, a kind (`free`, `paid`, `relay`), its platforms, a role line, whether it is a fallback, the host for the four configurable mirrors (kkinstagram, kktiktok, vxreddit, facebed), a traffic signal and, for `kkinstagram`, `kktiktok`, `vxreddit`, `facebed` and both relays, an hourly probe signal.
- **Signal state**: `ok` without a failure streak; for traffic, `stale` when the last failure is more than 24 h old (a probe never ages out: the dashboard calls it overdue instead); `down` at the alert threshold; else `degraded`.
- **Row state**, first match wins: `off` with an `off_reason` (in this order: `platform_off`, `not_configured` (no Apify or HikerAPI token, relay not usable), `not_listed` (not in `INSTAGRAM_PAID_PROVIDERS`), `special_off` (special downloads off: relays, Apify, HikerAPI), `relay_disabled` (the relay switched the platform off), `budget_paused` (from the `paid` snapshot, never a provider call)); then `down`, `degraded` or `ok` by the worst signal present; `stale` when only an aged-out traffic failure is left; without any signal `idle` for a fallback row and `unknown` otherwise. An off row still carries its signals.
- **Error codes**: `timeout`, `http_4xx`, `http_5xx`, `http_429`, `transport`, `parse`, `wrong_content`, `not_configured`, `other`, from the error type where a site holds the error, else from the detail text with its URLs removed, first match wins: an explicit HTTP status (the code right after "HTTP", "status", "status code" or "code", optionally with ": ", or Go's "<code> <reason>" form such as "504 Gateway Timeout"; so "probe HTTP 504 Gateway Timeout" is `http_5xx`, while a number inside a URL or a word is no status), then timeout words, "Too Many Requests", "not configured" texts, transport, parse and wrong-content words, else `other`.
- **Shape**: `version` (1), `started_at`, `computed_at`, `restored_from` (or `null`), `services` (always an array, in catalog order): `key`, `label`, `kind`, `host`, `platforms`, `role`, `fallback`, `has_traffic`, `has_probe`, `state`, `off_reason`, `traffic`, `probe`; a signal has `state`, `last_success_at`, `last_failure_at`, `failing_since`, `consecutive_failures`, `threshold`, `last_error_code`. Every key is always present, `null` when empty; times are UTC RFC 3339.
- **Seeding**: at start, right after the settings were read from the database and before the first publish, the bot reads its last published `services` row (at most 2 s, `Store.LoadStatus`) and restores the streaks, thresholds, times and codes into the tracker (`services.SeedServicesHealth`, `Options.SeedServices`): future times are dropped, bad counts and thresholds fixed, unknown codes become `other`, a streak whose last failure time was dropped restarts at 0, signals with no time left are skipped, rows whose key is not in the catalog (such as `proxy-pool` and `reddit-proxy` from an older bot) are ignored, entries already there are never overwritten, and `restored_from` is set to that row's `computed_at`. An outage the owner was alerted about stays marked, so the next real success sends the usual recovery notice; seeding itself never alerts, and since the alert rate limit does not survive a restart, a new outage alert needs the key's threshold of new failures in a row after the restart (the seeded streak stays shown). The `services` component is not published until that read succeeded or found no row, so the stored row is never replaced by an empty health: a failed or slow read is logged and retried at the next successful reload (every 60 s), while the other components publish as usual; a bad row is logged and the health starts empty. When the start's settings read failed (cache file or `.env`), the seed runs at the first successful reload; with a database that could not be opened at start, or none, there is no seeding and nothing is published.

## Settings goroutine (`services/botsettings`)

One goroutine owns the snapshot the getters read (`config/overrides`, lock-free), so a reload can never undo an apply:

- **Start**: loads `bot_settings` before the startup checks, so the first profile push already follows it. The read and the first publish each get at most 5 s (`startupTimeout`); a read that fails or takes longer counts as the database being unavailable. Then the bot uses the cache file `var/settings-cache.json` (git-ignored, written atomically after the start's load, every apply and every reload that changed the values; a write failure is logged once until a write succeeds again) and alerts the owner once: only the keys set in the dashboard come from the cache, every other key still comes from `.env` or its default. Without a cache file it uses `.env` and the defaults, also with one alert. When the connection was made but the read failed, the first successful reload (every 60 s) switches to the database values. When a configured database could not be opened at start (`InitDatabase` failed; `app/settings.go` passes its error as `Options.DatabaseErr`, no further database call), the bot uses the cache file or `.env` the same way with one alert, but runs no loop and publishes nothing: it does not reconnect, so the alert asks for a restart once the database is back. Without a database configured the settings stay inert (above) and a leftover cache file is ignored.
- **Every 2 s**, with `Options.ApplyRequests` on (`app/settings.go` turns it on; the heartbeat publishes it as `applies_requests`): claims the oldest queued request (`FOR UPDATE SKIP LOCKED`), checks the key, the value (type, range, ceiling), that the current value still equals `expected` ("changed meanwhile, reload") and the approval rule, then writes `bot_settings` and the request's outcome in one transaction, or moves a request that needs approval to `awaiting_approval` (see "Telegram approval"). The snapshot changes only after the commit. While the bot runs on the cache file, requests wait for the first successful reload. Every 2 s, before that, it marks the queued and awaiting requests past their `expires_at` (the DB's clock) `expired`, so a stale request never keeps its key's open-request slot; with `Options.ApplyRequests` off (tests only) that is all it does.
- **Every 60 s**: re-reads `bot_settings` (picking up manual `psql` edits) and publishes the heartbeat, the secrets and the settings. `settings_loaded_at` in the heartbeat is the time of the last successful read, changed or not. A failed read keeps the current snapshot.
- **Change digest**: every applied change (from a request, and every key a reload finds changed outside the bot, e.g. by `psql`) goes into one plain-text Telegram message to the owner, at most one per 5 minutes: the first at the next 2 s tick, later ones once the 5 minutes have passed, the pending ones at shutdown. Each line is the bot's own rendering from the registry label and the old and new effective values, with the time (Kyiv) and the actor, e.g. "• TikTok off (21:40, dashboard)"; no text from the dashboard. It can not be muted, so a change nobody announced still reaches the owner. A failed send is retried in the next window; more than 20 changes end with "…and N more".
- **Telegram approval** (`services/botsettings/approval.go`, `app/settings_approval.go`): see below.
- **Profile**: after a change it re-renders the Telegram profile (command menu, description, short description) 10 s after the last change and pushes only the parts that differ from what Telegram shows, making up to 5 attempts with a growing wait, then alerting once. The platform lists of the description, the short description and `/start` / `/info` are built from the platform switches.

## Telegram approval

A request whose change needs approval (`setting.NeedsApproval(current, next)`, the registry's rule) is not applied at once:

1. In the claiming transaction the bot sets it to `awaiting_approval` (`needs_approval = true`, `expires_at = now() + 15 min` on the DB's clock) and commits. At most 3 requests wait at once; a 4th is rejected ("too many changes waiting for approval"). Without `ADMIN_USER_ID` it is rejected as above.
2. It sends the owner (`ADMIN_USER_ID`, the private chat) a plain-text message rendered only from the registry and the validated values, with no text from the dashboard: "⚙️ The dashboard asks to change a setting:" / "Apify monthly budget (USD) 4.8 → 6" / "Request #42, expires at 21:55 Kyiv time.", with the buttons ✅ Approve (`setappr:<id>`) and ❌ Reject (`setrej:<id>`). The message id is stored in `approval_message_id`. If the message can not be sent, the request is rejected ("could not ask the owner in Telegram"), so it never waits for a message the owner did not get. Each Telegram call of the approval (the ask and every edit) gives up after 15 s, since it runs on the settings goroutine; an ask that timed out is rejected the same way, and if that message still arrives, a tap on it removes its buttons.
3. A tap is accepted only from `ADMIN_USER_ID` in the private chat with the bot; anyone else, or a tap in a group, gets a short refusal and changes nothing. The callback goroutine only hands the tap to the settings goroutine (a channel its loop selects on) and waits up to 10 s for the answer; the settings goroutine stays the only writer of the snapshot and handles the tap between its other steps, so a reload can not undo it either.
4. Approve runs in one transaction: a conditional claim (`UPDATE … SET status = 'applied' WHERE id = $1 AND status = 'awaiting_approval' AND expires_at > now() RETURNING …`), then the same checks as a direct change (the current value must still equal `expected`, else "changed meanwhile, reload"; the value is validated again), then the `bot_settings` write with actor `dashboard` and the audit note "approved in Telegram"; a failed re-check turns the claim into `rejected` in the same transaction. It applies exactly the change the message showed. After the commit the snapshot, the cache file, the published settings, the profile re-push and the digest ("dashboard, approved in Telegram") follow as for a direct change. Reject is the same conditional update to `rejected` ("rejected by the owner in Telegram").
5. A double tap, a tap after a decision or a tap after the expiry matches no row and changes nothing: the answer is "Already decided." or "This request has expired." (a tap on an expired request the sweep has not reached yet expires it). Until the bot has read the database a tap changes nothing and the request keeps waiting: on cached settings the answer is "The bot is on cached settings; try again after it reconnects.", on `.env` and the defaults (the first read failed and there was no cache file) "The bot is on .env and defaults until it reads the settings database; try again later."
6. Every final outcome edits the message, keeping the change line and removing the buttons: "✅ Applied", "❌ Rejected", "⌛ Expired" (by the 2 s sweep), "Changed meanwhile, not applied" or "❌ Not applied: <reason>". Edits are best effort. A tap that changed nothing edits the message only when it may still show its buttons (the request expired, or its message id was never stored), so a double tap does not edit it twice. A rejected or expired request is never revived.

## Tests

```bash
go test ./model/settings ./config ./services/botsettings                    # registry, precedence matrix, goroutine (fake store)
SETTINGS_TEST_DSN=postgres://... go test ./services/botsettings             # plus migrations 001-013, 011 and 012 down/up, triggers, grants, races, approval transitions (two concurrent approves, approve against expiry), special-limit requests and the policy audit
GATED_FETCH_TEST_DSN=postgres://... go test ./services -run Relay            # relay history aggregate and pruning (migration 013)
```

The integration tests run the real migrations in their own schema and create a temporary role for the grants test, so point them at a throwaway database only.
